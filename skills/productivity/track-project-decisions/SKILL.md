# Track project decisions

## Use this skill

Use this when project choices need a current, connected record: what is settled, what remains open and which answer unlocks dependent work. Reuse authoritative decisions and accepted context instead of reopening discovery.

Use `research-topic` to investigate a factual question, `challenge-proposal` to resolve choices in a candidate, and `create-tasks` for executable implementation work. Routine progress belongs in `report-project-status`.

## Establish the decision baseline

Read the intended outcome, constraints, existing records and relevant current evidence. For an inherited project, preserve behavior, data and operating commitments. For a new project, distinguish missing foundations from genuinely unresolved product or technical choices. Do not invent historical rationale or promote a proposal to an accepted decision.

Identify choices that affect feasibility, scope, architecture or sequencing. Record each question, why it matters, evidence, credible options, owner where known, dependencies and current state. Use [the decision template](references/decision-map.template.md) when a durable map is needed, adapting the existing authoritative location rather than creating another decision store.

## Investigate and maintain the record

A dependency means one decision needs another answer; it is not an implementation ticket. For example, a hosting choice may depend on the data-residency requirement. Keep unknown areas coarse and select the next consequential investigation or conversation that is ready.

Investigate independent questions in parallel only when they do not rely on unsettled shared assumptions. Reconcile their evidence before updating the same record. Preserve accepted choices and reopen them only when new evidence changes a material premise. When superseding a decision, retain its source and explain which dependent work must be reconsidered.

Record actual acceptance and owners only when established. Remote updates and messages need their actual authority. Leave dependent implementation blocked where required behavior or constraints remain unknown; other sufficiently settled portions can proceed.

## Result and verification

Return changed decisions, affected dependent work, the next ready question and evidence that would settle it. Follow the requested audience/depth and project format, linking accepted records instead of copying them.

Check statuses against acceptance evidence, dependencies against actual prerequisites, and unresolved questions against their consequence. Before acceptance, have a separate agent in fresh context challenge the raw request, candidate map and source records without the author's conversation or preferred conclusions. Retain its returned reviewer/session identity, evaluated artifact or revision, findings and coverage. Reconcile unsupported choices or stale dependencies and independently recheck affected records after fixes. Without that assessment, report the result as unreviewed.

## Next steps

Use `research-topic` for a ready factual investigation or `challenge-proposal` for a decision requiring focused questioning. Pass settled scope to `write-spec` for behavior, `design-architecture` for technical structure or `plan-phases` for delivery milestones once their relevant prerequisites are accepted. Carry decision IDs, evidence, dependencies and remaining gaps; check availability or give the plain action.

Continue ready work already authorized without waiting for the entire initiative to be settled. A decision-map-only request can end with the updated record and next question.

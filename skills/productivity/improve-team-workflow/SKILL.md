# Improve team workflow

## Use this skill

Use this for a recurring way the team gets work done, such as intake, review handoffs or release coordination. Produce a supported diagnosis and trial proposal, or assess an authorized trial. Reuse existing agreements, recent records and accepted constraints.

`find-improvements` discovers code-level candidates; `plan-phases` defines feature milestones; `automate-code-checks` implements an accepted recurring coding guard. A process map, meeting or tool is useful here only when it addresses the demonstrated problem.

## Trace the actual process

Establish the process, participants, trigger, useful outcome, recurrence and requested stopping point. Read current agreements, ownership and representative records before asking people to reconstruct recorded facts. Preserve settled product requirements and controls.

Trace inputs, decisions, handoffs, queues, active work, waits, rework and recovery. Compare documented procedure with observed practice. Record owners where established; missing timestamps do not prove missing activity, and activity counts do not establish individual productivity. Use only personal or customer information needed for the process question.

Separate symptoms from possible causes. Follow ordinary and delayed or failed cases to test where work waits or loses required information. Distinguish avoidable delay from necessary review, safety, approval or compatibility checks. Elapsed review time alone does not establish missing ownership.

## Design one useful trial

Compare a small set of credible changes, including retaining the current process when evidence is weak. Prefer repairing an existing handoff or removing demonstrated duplication before adding a platform or ceremony. Explain the proposed mechanism, trade-off and uncertainty; expected savings remain a hypothesis.

For measures, alternatives or trials across stages, use [the workflow trial playbook](references/workflow-trial.playbook.md). Define the change, agreed owner, eligible work, duration or sample boundary, baseline, success signal, preserved controls, stop conditions and recovery. Missing ownership, access or decisions remain prerequisites.

When automation is proposed, use [the automation comparison](references/workflow-trial.playbook.md#when-automation-is-a-candidate). Compare removal/simplification, manual work, existing native features, deterministic automation and AI assistance where credible. Count setup, human review, exceptions, maintenance and recovery before claiming savings. A recommendation grants no procurement or deployment authority.

Preserve required approvals, independent review, privacy, security and acceptance checks. Obtain the actual decision owner's agreement before changing an established control. Do not redefine “done” or exclude difficult work to improve a metric.

## Run or assess within scope

A proposal request ends with the trial design. For authorized execution, use the existing tools and agreed bounds; messages, assignments, automation, policy changes and remote writes still need their actual authority. Missing tools can leave a useful proposal without a claim that it ran.

Compare equivalent work, definitions, windows and conditions. Record workload, staffing, holidays, other initiatives and missing observations. Inspect quality, rework and effort shifted to other roles alongside speed. Coordinate trials sharing a queue, reviewer or mutable process because they can contaminate one another's comparison.

Recommend adoption, adjustment, a specific further observation or stopping. Small or changed samples may support no conclusion. Adoption remains a separate decision unless already authorized; update the existing process record within that authority.

## Result and verification

Return the problem, supporting records, trial contract or observed outcome, limitations and next action at the requested audience and depth. Use the project's existing format. For authorized PR work, include safe relevant proof and independent findings, refreshing affected evidence after edits.

Before acceptance, have a separate agent in fresh context challenge the raw request, candidate and source records without the author's conversation or preferred answer. It should test alternative causes, comparison validity and preserved controls. Retain its returned reviewer/session identity, evaluated artifact or revision, findings and coverage. Reconcile defects and independently recheck affected results after changes. Without that assessment, label the result unreviewed; without trial observations, do not claim measured improvement.

## Next steps

Use `create-tasks` for accepted implementation needing decomposition, `automate-code-checks` for a selected repeatable coding guard, or `report-project-status` for an audience update. Pass the hypothesis, baseline, accepted decision, constraints and unmet prerequisite. Check availability or describe the plain action; continue only ready work already authorized. No change or a completed bounded trial can be the final result.

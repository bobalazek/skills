# Resume and recovery

Use when work was interrupted, a branch failed or an external operation has an uncertain outcome. Preserve the project's states and identifiers; the distinctions below need not become new status names.

## Reconstruct before acting

Read the accepted definition/version, original authority, current record, source workspace, pending questions and raw results. Inspect the actual worker or provider state when available. An elapsed interval or a person's “done” is a lead to verify, not proof of platform completion or permission to take another owner's work.

| Observed state | Safe next step |
| --- | --- |
| Prepared, never started | Recheck prerequisites and authority; start only when ready |
| Running or submitted without a terminal result | Inspect the existing task or operation ID; retain pending state and avoid replaying the write |
| Artifact returned, checks or required review missing | Keep it submitted/unreviewed and block consumers that require acceptance |
| Accepted output, unchanged applicable contract | Reuse its valid proof and continue the next ready consumer |
| Definition, input or source revision changed | Identify affected contracts/evidence; reconcile the consequential change and preserve unaffected proof |
| Failed branch | Retain its evidence and partial output, block its consumers and repair only the authorized cause |
| Cancelled or expired ownership | Follow the actual host's recovery/claim protocol; elapsed time alone supplies no reassignment authority |

If state cannot be observed, record that gap before a consequential retry. Poll only within the agreed duration/rate and authority; a pending response does not justify an unbounded loop. A user-supplied continuation summary cannot upgrade an unsupported claim into accepted evidence.

## External effects and receipts

Keep the original operation or idempotency identifier, target, permitted effect and last observed result. Read back an uncertain write before submitting it again. An acknowledgement, request ID or process exit can precede the target's terminal state. A receipt needs the observed target state and relevant external ID, with time and source; it contains no secret value or unrelated personal data.

For a human step, retain the safe checkpoint, expected observable outcome and existing authority. The person enters credentials or codes through the service's intended interface. Confirm the resulting state before advancing. A session expiry can require a new access step without authorizing repetition of earlier writes or imposing a new approval on an already approved unchanged action.

## Repair, retry and cancel

Use the accepted retry limit and existing recovery path. Change the failed approach or input before retrying a known error, and refresh the affected checks. Keep unaffected accepted work; do not reset the entire run to hide a failed attempt.

Cancellation and rollback are separate effects. Observe which workers, jobs and external operations actually stopped; report in-flight effects that remain. Reversing accepted side effects, deleting outputs or changing shared source data needs its own authority and a verified recovery procedure.

Resume from the last verified state. Before final completion, reconcile the joined outputs and any refreshed acceptance evidence against the requested outcome, rather than summing phase-local successes.

# Report project status

## Use this skill

Use this to explain what changed, what is established now, what threatens the agreed outcome and what action is needed. Reuse accepted goals, status definitions and prior updates. A short report can be the complete result.

`prepare-handoff` carries context for an owner/session transfer; `plan-phases` defines delivery milestones. Reporting progress does not require either artifact or a new status system.

## Set the reporting boundary

Establish the project, audience, period/cutoff, requested format and accepted milestones. Name the time zone when it changes event membership. Ask only for missing context that materially changes the report. Use the previous update to identify changes, not to prove its claims remain current.

Inspect relevant scope records, tracker entries, PRs/revisions, verification, deployment/release state, acceptance decisions and operating signals. Match each source to what it can establish. Preserve source links, observation times and material versions; missing access limits coverage rather than preventing every useful statement.

## Reconcile the evidence

Trace claims to actual work, artifacts, revisions and environments. Separate proposed, in progress, implemented, reviewed, merged, deployed and accepted where it matters. A closed ticket, merged PR or build proves neither production delivery nor acceptance. Resolve conflicts using definitions and evidence, retaining unresolved discrepancies instead of selecting the most favorable label.

Separate events within the period from older work newly discovered or updated. Compare against agreed scope, identifying added, removed, reopened or deferred work. Preserve acceptance gaps. For parallel phases, distinguish accepted outputs, ready independent work, blocked consumers and missing integration evidence.

For conflicting systems, interpreted metrics or recurring reports, use [the status evidence and update guide](references/status-update.template.md). Metrics need definitions, denominators, sources and periods. Do not infer completion, productivity or savings from ticket counts or elapsed time. Label forecasts with their source, assumptions and dependencies; a target remains different from an observed outcome.

## Write and, when authorized, publish

Lead with the material outcome and change. Include evidenced results, current work, consequential blockers/risks, and the next action or decision. Use established owners and dates only. Apply project health labels only when their criteria and evidence support them.

For example, “merged and deployed to staging” can coexist with “production and acceptance unverified.” Do not rewrite tracker state to make records agree.

Match sensitive content and detail to the audience, requested depth and project format. Drafting does not authorize sending, changing commitments or updating trackers. For authorized publication, use the specified destination and verify the stored result without widening its audience.

## Result and verification

For substantive wording cleanup, use `review-writing` when available; otherwise remove empty praise and repetition locally. Keep completion states, dates, ownership, uncertainty and blockers intact. An improved tone must not make the project look healthier than its evidence supports; reuse a valid writing assessment rather than adding a compulsory second pass.

Return the update with nearby evidence, cutoff, coverage limits and exact next action. Reuse the authorized reporting location. For authorized PR reporting, retain accessible proof and independent findings, refreshed after affected changes.

Before acceptance, have a separate agent in fresh context check the raw request, candidate update, source records and permitted checks without the author's conversation or preferred conclusion. It must test completion, health and forecast claims. Retain the returned reviewer/session identity, evaluated update or revision, findings and coverage. Reconcile defects and independently recheck affected claims after corrections. Without that assessment, label the update unreviewed.

## Next steps

Use `verify-change` for missing acceptance proof, `track-project-decisions` for consequential unresolved choices, or `improve-team-workflow` for a selected recurring process problem. Use `prepare-handoff` only for an actual transfer. Carry the cutoff, source versions, agreed outcome and exact gap; check availability or describe the plain action. Continue ready work already authorized, or finish a status-only request with the report.

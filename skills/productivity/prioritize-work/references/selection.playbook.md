# Work selection playbook

Use this when several supplied candidates compete for capacity, deadlines or shared prerequisites. Keep the existing backlog and source IDs; the output is a decision about work, not a replacement specification or new task graph.

## Normalize only what affects selection

Record the goal and planning horizon, available capacity by relevant role/resource, existing commitments and the source of required deadlines. Capacity includes the work needed to reach acceptance, not only implementation. Identify known interruptions or reserves using the team's actual practice; do not invent a universal utilization target.

For each candidate, carry the following where available:

| Field | Decision it supports |
| --- | --- |
| ID, outcome and scope | Trace the item without silently changing what it promises |
| Current state and remaining work | Distinguish completed work, in-progress commitments and new starts |
| Goal contribution and delay consequence | Explain why this work matters in this horizon |
| Effort, estimate basis and uncertainty | Compare what is known without fabricating missing numbers |
| Required people, resources and checks | Expose bottlenecks hidden by an aggregate capacity number |
| Prerequisites and acceptance evidence | Distinguish ready work from work that can only follow another result |
| External input or decision | Name what is unavailable and who owns it where known |

Merge duplicate representations only when they describe the same work; retain links to the originals. A similar title does not prove duplication. Flag contradictions between a tracker and its authoritative scope or acceptance evidence before relying on the status.

## Make constraints visible

Separate hard obligations from negotiable preferences and explain their sources. If two required items compete for the same unavailable specialist, report the capacity conflict. A higher score cannot resolve it. Present the actual choices, such as reducing agreed scope, changing a date, obtaining capacity or deferring other work, with the decision owner where known.

Keep ranking and readiness separate. An important blocked item can remain high priority while a lower-ranked independent item is ready now. Mark dependencies whose completion could fit within the horizon without pretending their outputs already exist. An external promise or an open decision is not accepted prerequisite evidence.

When a necessary prerequisite is absent from the supplied set, flag it as required supporting work and show its effect on feasibility. Do not silently add a large project or create executable tasks from an assumed solution. Count a prerequisite once when several selected items share it, while retaining each dependent's own implementation, review and integration effort. Do not multiply a shared outcome's benefit across duplicate candidates.

## Compare without false precision

Use the simplest comparison that explains the trade-off. If the team already uses a scoring model, retain its definitions and inputs, check units and missing values, and show where a different reasonable assumption changes the order. Do not mix scores from unrelated scales or divide by labels such as small/medium/large.

Missing estimates may support qualitative ordering but not a numerical capacity total. Use explicit scenarios or ranges only when their basis is supplied or evidenced. Separate active work from external waiting time. Availability in one role cannot automatically cover work in another, and a worker count does not prove that tasks can safely run concurrently.

For work in progress, compare remaining benefit and cost, obligations and interruption/restart effects. Already-spent effort alone does not make an otherwise weak candidate valuable. Conversely, repeatedly starting high-ranked items without finishing their acceptance work can consume capacity without delivering the intended outcome.

## Return an actionable selection

Use a compact table or the existing planning record:

| Item | Selection and order | Readiness and prerequisite | Rationale and capacity | Next action or reconsideration trigger |
| --- | --- | --- | --- | --- |
| Supplied ID | Selected, deferred or awaiting decision; relative order when useful | Ready or blocked, with the accepted evidence or missing condition | Supported goal, obligation or trade-off; relevant role/resource | The condition or accepted action that changes its state |

Show the first ready item or batch and later selected work separately. Order depends on prerequisites and availability, not solely on benefit rank. A feasible selection is a planning assessment under stated assumptions, not proof that delivery occurred or a guarantee that estimates will hold.

## Adversarial checks

- Does the selected set omit a required commitment or silently assume another team will supply it?
- Is a highly ranked item shown as ready despite missing approval, access or accepted prerequisites?
- Are shared costs counted twice, required review omitted, or the same constrained person's time allocated more than once?
- Does a score conceal an unknown input or arithmetic across incompatible units?
- Would a plausible change in the weakest estimate or availability assumption change the recommendation?
- Does the proposed update exceed authority by assigning people, changing commitments or starting execution?

For example, two selected features may need the same enabling change and the same reviewer. Include the enabling work once, then check that the reviewer can cover both features and the enabling change. If that capacity is unavailable, return the reduced selection or explicit conflict; calling the features independent does not resolve the bottleneck.

# Design-system contracts

## Foundations

Token meaning and naming, typography/spacing/color or other needed foundations, themes, and supported surfaces. Keep raw implementation values separate from semantic meaning only where that distinction is useful.

## Components

| Component | Responsibility | Inputs/variants | States and accessibility | Consumers |
| --- | --- | --- | --- | --- |
| A repeated interface need | What it owns | Supported contract | Relevant behavior and checks | Actual screens or features |

Include concise usage and extension examples. Avoid variants for hypothetical future combinations.

## Governance and change

Authoritative design/code locations, extension criteria, ownership, verification commands/preview paths, and known exceptions. For a breaking change, state old/new contract, migration steps, affected consumers, compatibility/removal plan, and evidence that migration works.

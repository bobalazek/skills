# Foundation readiness

Track applicable items in the existing task or PR with observed evidence and the candidate/environment. Check a box only after its result is demonstrated. Failed or unperformed checks stay unchecked with the consequence and next action; mark inapplicable items with a reason. Refresh affected proof when the candidate or prerequisites change.

- [ ] Purpose and the first supported behavior are clear.
- [ ] Questions that affect the foundation were answered or explicitly delegated before setup; open choices still identify blocked work.
- [ ] The original request and accepted clarifications are retained in the existing brief/README/spec, with an outcome and source that later implementation and review can check.
- [ ] Supported app targets and exclusions are explicit: web/browser, responsive versus installed mobile, and desktop as applicable. Required OS/device/input, permissions, distribution and validation constraints are settled for the first path.
- [ ] The first demonstrated path serves that requested user outcome on the selected target. A starter demo, browser viewport or simulator is not proof of unexercised installed-app or device behavior.
- [ ] The selected runtime starts through documented commands; prerequisites and unavailable services are named.
- [ ] The first path has an accepted hosting/environment and process map, with relevant local or externally managed data/file, hosting/delivery, API/AI, MCP/tool and runtime/build dependencies, configuration names and operating owners. Missing consequential choices remain blocked; template resources are not automatically adopted or deployed.
- [ ] One representative path crosses the required real boundaries and has an observable result.
- [ ] Relevant lint/type/build/behavior checks run and their outputs are inspected; commands are not invented from package names.
- [ ] Configuration distinguishes safe examples from secret values. Generated output and local state have appropriate handling.
- [ ] Repository structure, dependencies, extension points, and contributor conventions fit the selected stack and project.
- [ ] Contributor guidance identifies the Git base/branch, commit and PR naming, merge strategy and applicable guards; remote checks/settings are not claimed from local setup alone.
- [ ] Setup docs describe this project, not an untouched starter demo. Agent instructions point to authoritative context without copying the entire documentation tree.
- [ ] Delivery expectations and remaining work are explicit; local success does not imply production readiness.

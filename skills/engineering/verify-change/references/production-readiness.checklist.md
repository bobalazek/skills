# Production-readiness checks

Use this self-contained reference for a production-readiness or launch assessment. It complements the change-level behavior checklist and does not require installing sibling skills or a commercial assessor.

## Production service checks

Select these checks for launch/readiness work, hardening findings or a change that touches the named surface. Routine leaf edits need only their affected checks. A feature named here is conditional on the product, supported users, contracts and credible risks; this list does not authorize buying services, provisioning infrastructure, inventing business policy or expanding the requested work.

For every selected criterion, retain its ID, applicability/source, expected outcome, observed result and evidence, tested revision/environment, accountable owner and any gap/next action in the existing task or review record. Use `demonstrated`, `failed`, `not checked` and `not applicable` with a reason. Missing access or an unanswered required policy decision stays open. Check a box only after the observation supports the criterion; code/configuration presence and a proposed test are insufficient. Reuse valid proof and independently recheck affected results after changes.

Choose existing mechanisms that meet the requirement. Schedule and staffing examples are conditional: agree backup/restore targets, access/patch review intervals, response coverage and performance budgets with their owners. One person may cover several responsibilities; the checklist assigns accountability, not mandatory job titles or headcount. Run active security/load/recovery checks only within their actual authorized scope, using dedicated accounts and safe isolated data.

### Identity and access

Ownership: Identity/security owner; support owns the approved recovery process. Name the actual accountable person/team in the work record.

- [ ] PR-002. Email login: Use an address containing a literal plus sign through signup/invitation, login and recovery. Check URL/form encoding, identity lookup and the approved normalization policy; do not silently strip tags or merge distinct accounts.
- [ ] PR-003. Password reset: Exercise a valid link, an expired link, a used link and concurrent reuse. Verify replacement/invalidation rules, account-enumeration behavior and the required session invalidation at the actual server boundary.
- [ ] PR-004. MFA is required by privilege, data risk or contract: Exercise enrollment, challenge and a lost-device recovery path. Check recovery-code reuse, recovery identity verification, factor replacement notifications and whether recovery can bypass the required assurance.
- [ ] PR-005. User sessions: Test configured idle/absolute expiry and termination of every session for one user, including refresh tokens and supported devices. Verify revocation reaches protected operations within the accepted window rather than only clearing one browser cookie.
- [ ] PR-006. A supported enterprise/customer identity contract requires SSO: Test sign-in, account linking, tenant/domain mapping, IdP outage and the approved emergency-access path with that identity provider. Record protocol and provisioning ownership; SSO is not a default requirement for every app.
- [ ] PR-007. The accepted SSO contract specifies SAML: Check the maintained library/provider configuration and exercise issuer/audience/destination/signature validation, expiry and replay rejection with test assertions. Verify metadata/certificate rotation and reject incorrect tenant mapping.
- [ ] PR-008. A customer requires SCIM or equivalent automated provisioning: Exercise provisioning, role/group changes and offboarding through the real supported interface. Verify deactivation also revokes existing sessions, keys and queued access within the promised window, including failed delivery/retry; document any propagation delay.
- [ ] PR-009. Multiple authorities or roles: Derive allowed actions, objects and fields from the actual permission matrix. Exercise both permitted and denied cases, privilege changes and alternate admin/API paths; add roles only when the product needs them.
- [ ] PR-010. User-owned resources: With dedicated authorized test accounts, change an object identifier and attempt the relevant read, update and deletion. Verify the server denies access before returning private fields or performing effects; include a legitimate owner request.
- [ ] PR-011. Multiple tenants: Exercise negative read/write cases across routes, joins, counts, exports/imports, jobs, files, caches and admin paths that carry tenant data. Use the project's actual scoped-query, schema, database or RLS model; code or folder separation alone does not establish isolation.
- [ ] PR-012. Support impersonation is an accepted feature: Check who may start it, required authorization, scope/duration and how it ends. Exercise start, sensitive actions and exit/revocation; audit the support actor and effective user without exposing credentials. Do not add impersonation merely to complete this checklist.
- [ ] PR-013. Login or recovery endpoints: Exercise configured throttles with controlled accounts and bounded requests. Verify identity/IP/proxy handling, reset behavior and safe responses; ensure distributed instances share limits where the threat requires it.
- [ ] PR-014. Account lockout or adaptive login controls: Exercise repeated failures, recovery and legitimate login after the protection triggers. Check attacker-induced denial of service, account enumeration, response timing and the authorized support/unlock path against the agreed availability policy.

### Data model and lifecycle

Ownership: Domain/data owner with engineering; recovery targets belong to the service owner. Name the actual accountable person/team in the work record.

- [ ] PR-001. Persistent domain data: Review entities, identities, relationships, cardinality, constraints and deletion rules with the domain owner. Exercise representative writes through each writer, including a rejected invariant and concurrent writes where relevant; an ER diagram alone does not establish integrity.
- [ ] PR-015. Schema migrations: Apply the migration to representative prior state and verify old/new readers and writers. Rehearse the chosen rollback or forward repair, including writes after cutover; record irreversible data loss and compatibility limits instead of assuming a down script reverses every effect.
- [ ] PR-016. Migrations on a live data store: Measure lock acquisition, transaction duration, resource use and batch/restart behavior in an authorized representative rehearsal. Check timeouts, deployment order and abort conditions against the availability budget; a fast run on tiny fixtures is insufficient.
- [ ] PR-017. Growing persisted collections: Inspect representative query plans, predicates, ordering, cardinalities and latency for critical queries. Verify useful indexes and their write/storage/deployment costs; an index definition or an arbitrary row count does not prove capacity.
- [ ] PR-018. Concurrent database clients: Measure or verify configured connection budgets across app replicas, workers and deploy overlap. Exercise burst, exhaustion, timeout and recovery; use pooling or the provider's existing mechanism where needed and prevent unbounded connection creation.
- [ ] PR-019. Durable state needs recovery: Agree RPO, retention and backup scope with the owner, then verify scheduled backups and failure alerts. Nightly backups are a candidate only if they meet that RPO; cover required files, configuration and provider data as well as database rows.
- [ ] PR-020. Backups are relied on: Restore a named backup into an isolated authorized environment and exercise application reads/writes plus relevant invariants and completeness. Record backup identity, measured RTO/data loss and missing dependencies; a successful backup job or row count alone is insufficient.
- [ ] PR-021. Recovery targets require recovery between snapshots: Verify point-in-time recovery or the accepted equivalent, required base backup/log chain, retention and encryption-key access. Rehearse recovery around an accidental deletion and validate the target time and subsequent-write loss; record unsupported intervals.
- [ ] PR-022. The product promises recoverable deletion: Exercise delete, hidden/search/export behavior, restore, uniqueness conflicts and final purge under the accepted policy. Choose soft delete, trash or another proven mechanism to meet that promise; do not impose soft deletes on every schema or retain data past required erasure.
- [ ] PR-023. Untrusted input crosses a server/worker boundary: Bypass the form and submit missing, malformed, oversized and forbidden fields through each relevant route or job. Verify server-side validation of shape, bounds and domain rules with a useful rejection and no unauthorized partial effect.
- [ ] PR-024. Dates, timezones or scheduled local times: Distinguish instants from dates and recurring local schedules; retain the required zone. Test daylight-saving gaps/overlaps, user-zone changes and serialization/display so a local 09:00 reminder follows the agreed rule; UTC alone cannot define recurring local time.
- [ ] PR-025. Names or free text: Round-trip an apostrophe through input, persistence, search, export and rendering. Parameterize queries and encode output at its use; valid names must survive rather than being stripped by a blanket sanitizer.
- [ ] PR-026. Supported user text: Round-trip emoji, combining accents and relevant right-to-left scripts through storage, length validation, search, UI and export. Check byte versus character limits and bidirectional layout where meaningful; technical fields may keep explicit syntax constraints.
- [ ] PR-027. Money: Use exact decimal arithmetic/storage or integer minor units under an explicit currency, precision and rounding contract. Test fractional arithmetic, zero-decimal and three-decimal currencies where sold, overflow, conversions and serialization; binary floating point or a universal two-decimal assumption cannot establish exact totals.
- [ ] PR-028. Multiple markets or currencies: Get the supported currency, rounding and tax rules from the finance/tax owner for each sold market. Test inclusive/exclusive totals, discounts, currency conversion where offered and rounding order against approved examples; unresolved legal/tax policy remains a decision gap.
- [ ] PR-029. A known next domain variation: Walk the accepted second-customer or product variation through identity, relationships, constraints, permissions and migration path. Preserve the current model's invariants; use an actual requirement rather than speculative extensibility or a generic schema.
- [ ] PR-030. Retried payments or other non-repeatable effects: Retry the same operation sequentially and concurrently, including provider success with local timeout/failure. Verify a stable idempotency identity, payload binding, scope, persistence window and reconciliation produce one intended charge or effect.
- [ ] PR-031. Repeated form or command submission: Submit the action repeatedly and concurrently, then retry after a slow response/restart. Verify deduplication at the durable effect boundary while allowing distinct legitimate operations; a disabled submit button alone is insufficient.
- [ ] PR-032. Paged collections: Exercise a deep page/cursor with representative volume, stable ordering, ties and concurrent inserts/deletes. Check allowed page sizes, authorization before pagination, query cost and the documented consistency limits; avoid loading the full collection to slice it.
- [ ] PR-033. Export is promised or needed for the accepted data-access obligation: Generate and open a representative spreadsheet/CSV export. Verify actor/tenant/field scope, completeness, Unicode, timezone/amount formats, formula-injection handling, large-export bounds and expiring access where needed; absent export is a scoped gap only when required.
- [ ] PR-034. CSV or legacy-file imports: Use approved fixtures with expected legacy encodings, BOM, delimiters, quoted newlines, malformed rows, duplicate headers and large inputs. Verify mapping, row errors, authorization, formula safety where opened, duplicate/retry behavior and atomic versus partial-apply reporting without silent data corruption.
- [ ] PR-035. Retention or contractual deletion rules: Map data purpose, trigger, period, legal holds, copies and responsible owner. Run a bounded fixture through expiry/deletion across primary, derived and downstream stores, then verify completion and failure handling; a policy document or scheduled job alone does not prove deletion.

### Application and supply-chain security

Ownership: Security owner and the relevant implementation/incident owner. Name the actual accountable person/team in the work record.

- [ ] PR-036. Secrets are used: Inspect source/history, built artifacts, configuration examples, logs, prompts and tool traces without printing secret values. Verify approved secret references and redaction prevent unintended disclosure to repositories or AI services; record the actual scan scope and omissions.
- [ ] PR-037. A credential was exposed or rotation is required: Use the authorized incident/rotation procedure to inventory consumers, issue the replacement, update deployments and revoke the old key. Verify the old key fails and required consumers recover; preserve audit evidence and exposure scope without reproducing the value.
- [ ] PR-038. Dependencies were added or generated: Verify the exact package name, registry/source, publisher/provenance, resolved version and lockfile against the intended dependency. Inspect lookalikes, install scripts, licensing and maintenance; a successful package installation does not establish that it is the intended project.
- [ ] PR-039. Third-party dependencies: Run the supported dependency/security checks against the candidate lockfile and deployed artifact where appropriate. Triage reachability, exploitability and supported fixes; assign owners and deadlines under policy, retaining false-positive rationale and required unresolved exposure.
- [ ] PR-040. Untrusted data reaches a sink: Validate the allowed structure at entry, then use parameterized queries, context-specific output encoding, safe URL/path/process APIs and a maintained HTML sanitizer only where HTML is allowed. Exercise the relevant sink; stripping every input indiscriminately can corrupt legitimate text without preventing injection.
- [ ] PR-041. Reachable application attack surface: Select applicable injection, XSS, CSRF, authorization and other current OWASP risks from the threat model. Trace trusted-code enforcement and run authorized negative cases with safe fixtures; a generic sanitizer, CORS policy or scan alone cannot establish protection.
- [ ] PR-042. File uploads: Exercise size/count limits, content/type mismatch, hostile names and the applicable malware/quarantine controls before release. Verify storage/access policy, non-executable serving, download authorization and cleanup; the scanning requirement and response to unavailable scanning follow the accepted threat model.
- [ ] PR-043. Browser cross-origin access: Verify the intended public/credentialed origin policy on preflight and actual success/error responses. Reject disallowed credentialed origins, handle credentials deliberately and keep server authorization/CSRF separate; a wildcard may be valid for intentionally public non-credentialed resources.
- [ ] PR-044. HTTP responses: Select headers for the response type and supported consumers, then inspect normal, redirect and error responses through the real proxy/CDN path. Verify applicable CSP/frame, MIME, referrer and transport policy without breaking required integrations; declarations alone do not establish deployed headers.
- [ ] PR-045. Sensitive transport or storage: Verify required TLS on relevant hops and encryption for databases, files, backups and devices under the data policy. Check key access, rotation/recovery and excluded paths; encryption does not replace authorization, and a provider feature does not prove this instance uses it.
- [ ] PR-046. Human, service or AI-agent access: Inventory effective privileges and scope credentials by role, environment and task. Exercise a denied privileged action and offboarding/revocation; avoid giving an agent production access its task does not need and record temporary-elevation expiry.
- [ ] PR-047. Audit or diagnostic logging: Trigger a representative success, rejection and privileged effect and inspect the emitted record. Verify actor/action/target/time/correlation and access/retention while keeping passwords, tokens, payment-card data and unnecessary personal content out of logs and exports.
- [ ] PR-048. Contract or risk assessment requires penetration testing: Confirm authorized scope, qualified tester, safe target, findings and retest evidence before the agreed milestone. An automated scan or an agent review cannot stand in for the contracted penetration test; missing scope/access remains open.
- [ ] PR-049. A security questionnaire or assurance claim is required: Map each answer to current control evidence, scope, owner and exceptions. Verify the actual environment and record untested claims honestly; do not claim a certification, penetration test or retention guarantee from source code alone.
- [ ] PR-050. A supported service receives vulnerability reports: Verify a discoverable disclosure contact, triage/escalation owner, acknowledgment and remediation workflow. Run an internal tabletop report through it and check secure handling of submitted evidence and the agreed response targets.
- [ ] PR-051. A device can reach production or hold production secrets: Rehearse a lost/stolen-device incident: session/key revocation, device protections, replacement access and log review. Verify recovery ownership and coverage of local caches, SSH keys, browser sessions and agent credentials without destructively testing a live device.

### Obligations and assurance

Ownership: Legal/compliance or assurance owner with security and the data owner. Name the actual accountable person/team in the work record.

- [ ] PR-052. SOC 2 assurance is contractually required or selected: Identify system boundary, applicable Trust Services Criteria, report type/period, policies, control owners and retained operating evidence. Confirm the independent CPA examination/report status with the assurance owner; a checklist or self-assessment is not a SOC 2 report.
- [ ] PR-053. Health information may be subject to HIPAA: Have the responsible legal/compliance owner establish whether the organization is a covered entity or business associate and whether the data/workflow is regulated PHI. Map required safeguards and data flows only for the established scope; a patient-related record alone does not determine HIPAA applicability.
- [ ] PR-054. A covered HIPAA business-associate relationship exists: Verify the required BAA or other permitted arrangement, service eligibility and restrictions for each relevant vendor/subcontractor, including an AI provider receiving PHI. Check actual configuration and onward flows before sending data; neither all health vendors nor every model use automatically requires a BAA.
- [ ] PR-055. Sensitive-record access auditing is required: Exercise viewing/search/export as well as updates through relevant entry points. Verify the audit captures the actual actor and record or scoped query without copying sensitive contents, and test access, tamper protection and retention under the established policy.
- [ ] PR-056. Payment cards: Establish PCI DSS scope and the merchant/provider responsibilities using the actual payment flow. Prefer hosted/tokenized handling where suitable and verify PAN/security-code leakage is absent from app stores, logs and analytics; outsourcing payment collection can reduce scope but does not remove all obligations.
- [ ] PR-057. An applicable erasure right or deletion commitment: Exercise an authenticated request against the data inventory, including tables, search, logs, processors and exports. Apply documented legal exceptions/holds and retention; for retained backups, verify restricted use, scheduled expiry and restore controls that reapply deletions before normal use. Do not promise immediate editing of every immutable backup or erase lawfully retained evidence blindly.
- [ ] PR-058. A residency or transfer constraint is accepted: Trace primary storage, replicas, backups, CDN, telemetry, support access and processors against the contract's exact definition and applicable transfer rules. Verify configured locations and test/inspect actual flows; an EU deployment label alone does not establish every copy stays in the EU.
- [ ] PR-059. Access reviews are required by policy or contract: Review effective human/service/agent grants, privileged roles and inactive accounts at the agreed interval, quarterly when specified. Retain the accountable owner's signoff and evidence that rejected access was removed; a calendar reminder alone does not close the review.

### Runtime, delivery and recovery

Ownership: Delivery/infrastructure owner with the affected service owner. Name the actual accountable person/team in the work record.

- [ ] PR-060. Multiple environments: Compare relevant runtime/dependency versions, schema, deployment configuration and critical integrations across development, staging and production. Record intentional differences and their test limits; separate secrets/data and verify staging cannot act on live customers accidentally.
- [ ] PR-061. Infrastructure must be reproducible: Verify the existing infrastructure-as-code or documented reproducible configuration covers required resources, permissions and recovery dependencies. Rehearse a safe reconstruction/drift check where warranted; do not introduce a new provisioning platform merely to satisfy this item.
- [ ] PR-062. Automated delivery: Verify required tests/static/build checks actually gate the current release artifact and cannot silently be skipped through the supported publish path. Exercise or inspect a controlled failed check; a workflow file or old green run is insufficient.
- [ ] PR-063. A rollback is part of the recovery plan: Rehearse the documented rollback command/process on the candidate's compatibility window and confirm artifact/config identity, authority and smoke checks. Distinguish code rollback from recovering new writes or external effects; one-click convenience is optional.
- [ ] PR-064. Availability requires deployment without an outage: Exercise the supported rolling/blue-green or equivalent path with mixed versions, readiness, draining, long requests and in-flight jobs. Measure interruption against the accepted budget, including migrations; do not promise zero downtime without proof.
- [ ] PR-065. Feature flags or staged exposure are required: Test safe defaults, targeting and authorization for both flag states, dependency outage, rollback and cleanup ownership/expiry. Verify a disabled feature cannot still execute through an alternate entry point; flags are optional rollout tools, not a substitute for data recovery.
- [ ] PR-066. Measured or contracted demand needs elastic capacity: Rehearse scale-out/in against explicit workload and resource limits. Check warmup, database/queue bottlenecks, state/session behavior, draining and cost ceilings; retain a simpler fixed-capacity design when it meets the accepted targets.
- [ ] PR-067. Geographic delivery or measured performance requires a CDN: Measure the relevant regions and verify cache keys, private-data bypass, invalidation, stale/error behavior, asset URLs and residency constraints. A CDN is conditional on the actual delivery requirement; enabling it alone cannot prove global speed.
- [ ] PR-068. Public domains and TLS endpoints: Verify DNS records/ownership, actual certificate hostname/chain/expiry, automated renewal and a failure signal with an owner. Exercise the documented renewal/recovery path safely and include relevant callback and mail domains.
- [ ] PR-069. Slow or asynchronous work: Use the existing queue/job mechanism where the response budget needs it. Verify registration, tenant/actor propagation, terminal status, cancellation and timeout behavior; acknowledge accepted work separately from successful completion.
- [ ] PR-070. Transient remote failures are retried: Exercise timeout, retryable/non-retryable errors, backoff with jitter where needed, maximum attempts/time and cancellation. Preserve operation identity and reconcile partial effects so a retry neither loses nor duplicates an order; avoid retry storms.
- [ ] PR-071. Jobs can exhaust retries: Exercise a poison item through the existing dead-letter/quarantine or failed-job path. Verify retention, alert/owner, diagnostic evidence and authorized replay that does not repeat completed effects; a specific queue product is not required.
- [ ] PR-072. Scheduled work can run on multiple instances: Trigger overlap, restart and an expired lease/lock or equivalent coordination path. Verify one intended effect, catch-up/timezone rules and visible failures; a singleton-looking scheduler definition does not prove duplicate execution is safe.
- [ ] PR-073. Caching: Exercise read-after-write, updates/deletes, tenant/key separation, expiry, dependency failure and invalidation. Verify the accepted staleness contract and prevent private data sharing; only add caching for an actual need.
- [ ] PR-074. A domain sends transactional email: Inspect actual DNS and received-message authentication for the intended sender using SPF, DKIM and the agreed DMARC policy. Verify sender alignment and the delivery path for reset/invitation emails; records alone do not prove inbox placement.
- [ ] PR-075. Transactional email: Exercise delivered, bounced and complaint events through authenticated provider callbacks. Verify suppression/retry policy, user/support visibility and required security-email recovery without repeatedly sending to invalid recipients.
- [ ] PR-076. Temporary files or retained object storage: Exercise lifecycle expiry and abandoned-upload cleanup with scoped fixtures. Protect active/legal-hold data, coordinate references and check deletion observability, storage classes/versions and the accepted retention/cost policy.
- [ ] PR-077. Metered cloud, external APIs or agents: Verify budgets/limits and cost anomaly alerts at the required account, workload and customer scope. Use a safe threshold/event test to observe delivery to the owner, latency and response action; billing alerts alone may not impose a hard spend cap.
- [ ] PR-078. Service recovery commitments: Keep a disaster recovery plan with dependencies, RTO/RPO, authority, contacts and restore/failover steps. Rehearse the relevant failure safely at the risk/contract cadence, annually when required, and record measured gaps and completed follow-up actions.
- [ ] PR-079. A regional failure would violate an accepted commitment: Verify the selected multi-region/failover design, data consistency, replication lag, DNS/traffic behavior, residency, capacity and credentials. Rehearse the agreed failure/recovery path and cost tradeoff; do not require a second region for every service.

### Signals and operational response

Ownership: Named service operator and responder; support owns customer communication. Name the actual accountable person/team in the work record.

- [ ] PR-080. An operated runtime: Trigger representative events and retrieve structured logs by operation/correlation and time. Verify useful fields, search/access/retention, clock handling and ingestion failure under the supported environment, with sensitive fields redacted.
- [ ] PR-081. Error aggregation is relied on: Exercise repeated and distinct faults through the actual runtime. Check grouping, version/context, deduplication, sampling and notification volume so one incident is actionable without hiding different failures; reuse the existing mechanism.
- [ ] PR-082. External availability is promised: Observe the service from an authorized location outside its own network and exercise the critical dependency/user path. Verify alerting on failure and recovery; an internal health endpoint alone cannot establish customer reachability.
- [ ] PR-083. Human response is required: Trigger a safe alert and verify routing, receipt, acknowledgment and escalation for the responsible person. Check thresholds, deduplication, maintenance suppression and actionability against known incidents; a configured destination is not delivered notification evidence.
- [ ] PR-084. An operated service has latency/error/throughput targets: Verify dashboards report those signals from the relevant environment with correct units, windows, freshness and population. Inject or observe a bounded known change and reconcile the chart with requests; a dashboard screenshot alone cannot prove its queries are correct.
- [ ] PR-085. Cross-service diagnosis requires tracing: Follow a test request through applicable services, queues and external boundaries using propagated correlation/trace context. Check sampling, redaction and gaps; a simple single-process app need not acquire distributed tracing.
- [ ] PR-086. An uptime/support commitment requires responders: Name the actual primary and backup, coverage hours and escalation path; a rotation can be one part of the existing team's arrangement. Test contact/acknowledgment within the required window and record uncovered hours rather than inventing staff.
- [ ] PR-087. An operator must respond to failures: Give actionable runbooks for the applicable symptoms, such as queue depth, with diagnosis, safe mitigation, stop conditions and escalation. Walk a representative failure using the runbook and record missing access or unsafe/obsolete steps.
- [ ] PR-088. An incident warrants a postmortem: Record impact, timeline, contributing causes and evidence without blame. Assign corrective actions and due dates, then verify their closure with a regression check or rehearsal; writing the report alone does not improve recovery.
- [ ] PR-089. Customers need a service-status channel: Verify the agreed status page or equivalent channel, update authority, incident workflow and customer access during the service's failure. Test a draft/tabletop update and recovery communication without publishing an unapproved incident.

### Test and acceptance evidence

Ownership: Engineering/QA and the accountable acceptance owner. Name the actual accountable person/team in the work record.

- [ ] PR-090. Isolated business rules: Derive unit assertions from accepted domain behavior rather than copying implementation. Exercise meaningful boundaries and failure cases, demonstrate that a relevant violation fails, and record the actual run and candidate.
- [ ] PR-091. Critical third-party API boundaries: Exercise the real client's serialization, authentication, response parsing and relevant failure/compatibility paths using an authorized sandbox or suitable contract fixture. Disclose substitutions; mocks alone leave provider behavior unproven, and a live call is not required for every low-risk edit.
- [ ] PR-092. Critical signup, checkout or other accepted journeys: Exercise viable end-to-end paths from the actual entry point through visible and durable outcomes, including the consequential rejection/recovery case. Record role, environment and provider substitutes; a successful page load or enqueue is insufficient.
- [ ] PR-093. A launch/capacity claim depends on load: Run an authorized non-production test with representative data, workload, concurrency, duration, latency/error targets and stop limits. Observe bottlenecks and recovery, retaining environment differences; do not infer launch capacity from code shape or tiny fixtures.
- [ ] PR-094. Tests use representative data: Use synthetic or approved de-identified fixtures reflecting relevant volume, skew, edge cases and permissions. Inspect for copied personal data/secrets and re-identification risk, isolate run-owned state and verify cleanup; resemblance to production does not permit copying production data.
- [ ] PR-095. A defect or regression is repaired: Retain the smallest useful reproduction and a check that distinguishes the defect from the fix. Exercise affected neighboring consumers and include the case in the existing harness where appropriate; do not treat unrelated green tests as repair proof.
- [ ] PR-096. Older hardware/browsers are supported: Use the accepted minimum device/OS/browser matrix or justified comparable constraints, including CPU/memory/input limitations and slow networks. Exercise the critical journey and disclose physical-device versus emulated evidence; do not impose a specific laptop age universally.
- [ ] PR-097. Accessibility requirements apply: Establish the applicable legal/contractual standard, level and supported surfaces with the owner. Combine relevant automation with keyboard, screen-reader, focus, zoom/reflow and error-flow checks, recording scope and gaps; a scan alone cannot certify conformance.

### Billing and reconciliation

Ownership: Finance/billing owner with engineering; tax policy needs the accountable specialist. Name the actual accountable person/team in the work record.

- [ ] PR-098. Subscription billing: Exercise create/renew, upgrade/downgrade/cancel and relevant effective dates/proration with provider callbacks and entitlements. Check concurrent requests, stale plans, timezone/period boundaries and provider/local divergence against approved examples.
- [ ] PR-099. Recurring payments can fail: Exercise failed payment, retry/dunning, customer recovery and final unpaid/cancel state in test mode. Verify notice timing, duplicate suppression, grace/access rules and reconciliation without sending real collection emails or charging customers.
- [ ] PR-100. Procurement requires PO numbers or invoice fields: Carry the accepted PO/reference and required customer details through draft, issued invoice, export and corrections. Verify ownership, rendering and immutability/credit-note rules with finance; the invoice must match accepted purchasing terms.
- [ ] PR-101. Sales tax or VAT obligations apply: Use approved jurisdiction, product, customer/exemption and effective-date rules. Reconcile representative domestic/cross-border cases, evidence and invoice totals with finance/tax authority guidance; do not invent registrations or rely on a tax-library default as policy.
- [ ] PR-102. Refunds or credits: Exercise full/partial refunds, credits and repeated/concurrent requests through provider and ledger. Verify caps, currency/rounding, tax/proration, authority, final balances and reconciliation after provider success/local failure.
- [ ] PR-103. Usage-based billing: Reconcile billable events, deduplication, late corrections, windows/timezones, units and approved precision to the customer invoice. Test replay/missing events and boundary amounts; distinguish estimates from final charges and investigate unexplained differences.
- [ ] PR-104. Annual or custom commercial terms are supported: Verify accepted term lengths, prices, renewal/cancellation dates, negotiated exceptions and entitlement changes through billing and contract records. Test effective-date transitions and approval provenance; unsupported custom terms require a decision before a sale commits the system.
- [ ] PR-105. Finance/revenue reporting: Reconcile invoices, payments, refunds, credits, taxes, fees and timing to authoritative provider/ledger records under the approved accounting basis. Surface missing, late or stale data and preserve source/version provenance; matching aggregate row counts alone is insufficient.

### APIs and integrations

Ownership: API/integration owner with customer-facing support where relevant. Name the actual accountable person/team in the work record.

- [ ] PR-106. Incoming webhooks: Verify provider-specific signature over the required raw payload, timestamp/replay window and secret rotation. Exercise invalid/missing signatures and tenant/source mismatch before side effects; a parsed-body signature test may miss the real transport path.
- [ ] PR-107. Webhook delivery or receipt is retried: Exercise timeout, non-success, duplicates and out-of-order events. Verify bounded retries, durable delivery status/logs, reconciliation and authorized replay at both applicable ends; signing alone does not prevent duplicate effects.
- [ ] PR-108. An API has supported external consumers: Check the established version/compatibility contract, old-client behavior, error/schema changes and deprecation notice/window. Exercise relevant old/new consumers and document breaking migrations; use the existing version strategy rather than requiring a new URL scheme.
- [ ] PR-109. Customer API credentials are offered: Exercise scoped creation, one-time secret display/storage, rotation, expiry where used and revocation. Verify revoked keys fail through all supported entry points within the promised window and audit who manages tenant keys.
- [ ] PR-110. An integration API needs resource protection: Exercise quotas/burst limits per the accepted key/tenant/identity model and realistic legitimate workload. Verify fair limits, retry guidance and overload behavior without leaking another tenant's use; do not prescribe arbitrary fixed limits.
- [ ] PR-111. Third-party response formats can change: Check supported provider versions, validated parsing of required fields, unknown/missing fields and meaningful failure visibility. Rehearse a contract drift fixture and document monitoring, version pin/deprecation tracking and the owner's repair/reconciliation path.
- [ ] PR-112. OAuth access/refresh tokens: Exercise expiry, refresh, rotation/reuse rejection as supported, concurrent refresh, invalid_grant and revoked consent. Check secure token storage and reconnection without duplicate account linking or lost user work; use the provider's actual contract.
- [ ] PR-113. Customers are promised integration testing: Verify the supported sandbox/test mode, isolated credentials/data and representative request/event examples. Exercise a full sample and confirm test actions cannot charge, email or mutate production; document test/live differences.

### AI and agent behavior

Ownership: AI feature owner with security/privacy, cost and approval owners. Name the actual accountable person/team in the work record.

- [ ] PR-114. Untrusted content reaches a model or agent: Trace user fields, retrieved documents and tool output as untrusted.

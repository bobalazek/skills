# Backend evidence to probe

Use after identifying the affected task and authorized workload. Match the observed symptom to a falsifiable probe; these rows make no claim about cause frequency or a universal latency budget. Reuse existing instrumentation and report unavailable evidence rather than configuring monitoring by default.

| Observed evidence | Probe the specific hypothesis | Change only if supported | Preservation and comparison |
| --- | --- | --- | --- |
| Query count grows with returned parents | Count executed statements for several controlled result sizes through the actual consumer; inspect the repeated query and bound parameters. | Batch related lookups or use an appropriate join/loader. | Same tenant/filter/order, missing-child behavior and completed result; batching must not create a Cartesian explosion or unbounded response. |
| Time attributed to one query/access path | Inspect the version-specific plan and representative selectivity, rows examined/returned and indexes; compare with actual query timings. | Correct the demonstrated predicate/index/data-access mismatch through the existing schema process. | Matching data distribution, collation/case/Unicode semantics and ordering ties. An index being present or usable is not proof of a useful latency change. |
| Repeated write/commit overhead dominates a bounded operation | Count statements/round trips and transaction time for the same accepted rows; compare a bounded batch through the actual writer, including one rejected row and interruption. | Use a supported set-based/batched write or transaction grouping when it removes the measured cost. | Per-row validation, authorization, ordering, partial-failure reporting, atomicity and retry identity must match the contract; larger batches can increase lock time and failure scope. |
| Slow requests wait for connections | Separate acquisition wait from query execution and transaction lifetime; correlate concurrency, errors and active work. | Release held resources, shorten supported transaction scope or tune a justified limit. | Same useful throughput/error rate; raising pool size can move contention into the database. |
| Intermittent delay on otherwise fast writes | Correlate transaction spans, lock waits, hot rows and competing work in an authorized environment. | Reduce unnecessary work while holding locks or address a demonstrated contention point. | Atomicity, ordering and invariant checks; a fast uncontended microbenchmark does not establish contention relief. |
| Dependency span dominates completion | Measure connect/transport/service time, retry amplification and the user's actual required outcome. | Reuse an appropriate connection, remove redundant calls, bound supported concurrency or defer work only when the contract permits it. | Deadlines, idempotency, rate limits and terminal delivery; a faster queued acknowledgement can leave the user waiting longer. |
| Repeated expensive reads | Check repetition, key cardinality, reuse window and mutation/freshness requirements. | Per-request reuse or a bounded cache with a justified invalidation/eviction design. | Tenant/permission separation, revoked access, stale values, memory and failure behavior. Do not cache sensitive results merely because they are expensive. |
| Payload/serialization or retained memory dominates | Measure bytes/allocations and consumption through the real reader; inspect required fields and retention lifetime. | Project needed data, bound collections or stream where the consumer supports it. | Same information, order, backpressure, cancellation and peak/steady-state work. Missing fields or incomplete processing are not equivalent speedups. |
| Hot CPU/logging span | Profile the actual operation and compare with logging disabled/sampled only in a safe experiment when appropriate. | Remove proven redundant computation or expensive diagnostic work through existing logging policy. | Required audit/error records, diagnostics and privacy; avoid attributing CPU time from source appearance alone. |

Plan tools have different semantics. PostgreSQL [EXPLAIN](https://www.postgresql.org/docs/18/sql-explain.html) with `ANALYZE` executes the statement; analyzed mutations can change state. SQLite [EXPLAIN QUERY PLAN](https://www.sqlite.org/eqp.html) is a high-level diagnostic with version-dependent output, not a stable parser contract or a latency benchmark. Use the exact installed engine's documentation before relying on either.

A useful report names the hypothesis, command/probe, fixture and engine/runtime, raw observation, interpretation and next experiment. Keep diagnostic evidence, measured latency and production-capacity claims separate. A local engine can establish the local query/algorithm behavior while leaving production locks, driver behavior or remote service performance unchecked.

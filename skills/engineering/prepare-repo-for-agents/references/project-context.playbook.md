# Project context

Start from a real task on the target surface. Improve how an agent finds the facts, rules, and checks that task needs. A repository with useful documentation may only need a repaired link or a shorter instruction file.

## Inspect before creating

Locate root and scoped instructions, README/contributor entry points, documentation indexes, standards, architecture records, task records, and existing memory or learning systems. Inspect relevant package/workspace manifests, tool configuration, and CI to confirm commands and scope. Record a missing pointer separately from missing content.

Check current code and configuration when a document makes a technical claim. A commit establishes what changed; its rationale needs separate evidence. Distinguish an accepted decision, proposed choice, observed pattern, assumption, and superseded record. An observed pattern or remembered preference does not become a mandatory rule by being added to an instruction file.

When sources conflict, follow the host's verified instruction scope and the project's authority rules. Fix stale content at the owning source when the evidence and task authorize it. Expose an unresolved decision instead of inventing precedence. Do not create a second standards tree to avoid reconciling the first one.

## Keep one home per purpose

| Information | Authoritative home | Agent entry point needs |
| --- | --- | --- |
| Purpose, setup, main entry points | README or existing contributor front door | A pointer and any task-specific prerequisite |
| Local agent constraints and conditional reading | Applicable instruction files | The constraint or short task-to-source rule |
| Contributor rules | Existing conventions/standards documentation | Which standard applies to which surface |
| Current architecture, behavior, data, operations | Maintained project or surface docs | Owning area and relevant source/check links |
| Consequential choice and alternatives | Existing decision/ADR location | Index plus accepted/proposed/superseded status |
| Verified observation or recurring lesson | Existing memory/learning record when worth retaining | Index and the condition under which the record is relevant |
| Incident timeline and recovery | Incident record and maintained runbook | Operational boundary and relevant recovery pointer |
| Work status and dependencies | Existing task system or plan | A link when it affects the current task |

Keep detailed record lifecycle and factual knowledge work in project documentation. Agent preparation owns discoverability and applicability. Route substantial missing knowledge to `document-project`; unresolved contributor policy belongs to `define-project-conventions`. These next steps need no sibling package files to make the current navigation improvements usable.

## Write a short task path

Instructions should tell an agent where to read next, which unusual local constraints apply, and how to get feedback. Use the repository's existing instruction format. A small conditional map can cover its actual surfaces:

| Task condition | Pointer to provide |
| --- | --- |
| Any change | Main entry point, applicable root rules, and the scoped-check selection rule |
| A package or feature | Nested instructions, owner, canonical conventions, and representative implementation |
| A data/schema change | Data invariants, migration/recovery rules, and the appropriate safe check |
| A UI change | Existing components/tokens, accepted design, accessibility rules, and rendered checks |
| Deployment or external effects | Relevant operational instructions, prerequisites, and authority boundary |
| A known recurring failure | Relevant current lesson or incident record and the check that detects it |

Include only rows the repository needs. Do not copy a full tree, every memory entry, entire checklists, general engineering advice, or standards text into the agent entry point. A link needs enough context to say when to follow it. Nested instructions should add local differences and point to shared rules without repeating them.

For a representative task, map the instruction scope to the authoritative coding standard, relevant local example, exceptions, and a command or behavior check. Distinguish accepted rules from observed practice and enforcement. A formatter, linter, compiler, contract check, and behavior test cover different properties; a green command proves only what it inspected.

## Make memory indexes useful

Discover the existing index and entry format before proposing another memory folder or file. Verify that relevant index entries resolve, use understandable topics, and lead to evidence with an applicable surface, status, and source revision/date where needed. Keep the index short enough to select a record without loading the whole archive.

For the task path being repaired, check whether referenced advice is current, conditional, disputed, or superseded. Follow supersession pointers and compare material claims with current code or accepted decisions. A stale incident workaround must not override a fixed implementation. If a record's status cannot be established, expose that uncertainty and the check needed before applying it.

Repair broken pointers and status summaries within scope. Do not delete useful history merely because it is old, duplicate a record into several indexes, or convert a tentative learning into policy. A missing decision or evidence record is a knowledge gap; a pointer to a nonexistent record does not fill it. Reuse the project's existing lifecycle or hand record maintenance to `document-project`.

## Verify commands and discovery

Check that each documented command exists, runs from the stated working directory, and loads the intended configuration. Identify scoped versus full checks, environment prerequisites, expected output, and any destructive or external effects. Prefer safe existing checks. Record access requirements without copying secret values, and do not execute a deployment or destructive command just to prove that it exists.

Inspect the configured client and its project instruction discovery before editing tool settings. Use its existing mechanism and task-local references. Do not assume a particular filename, nested scope rule, ignore setting, or client integration works across hosts. When discovery is part of the request, exercise the target client's actual path and state the checked client/version or configuration. Reading the file manually establishes content, not automatic loading.

Optional indexes, CLIs, plugins, connectors, and runtimes remain optional unless the project requires them. Give an ordinary source/command path when an optional tool is absent. Repository preparation does not authorize global settings, new credentials, external integrations, or changes to application behavior.

Recurring violations may justify an automated guard after the invariant is accepted. Reuse existing tooling, check allowed and forbidden cases, and account for legacy violations. Do not expand agent prose to compensate for an enforceable rule or silently enforce an unsettled preference.

## Walk the result

Trace a representative task using only the revised entry points: find the owning code, applicable standards, current decision or lesson, preserved contract, and safe feedback loop. Include a nested surface if scope changes there. Check that links resolve and that obsolete records cannot look authoritative. Run relevant available checks and report their actual results and gaps.

A useful result can be a few repaired pointers. Add a document only when it has distinct content and an audience or lifecycle the existing home cannot serve. Keep the instructions short enough that the task's code and evidence remain the main context.
